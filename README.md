# YOSS 地域資源機能の再設計プロトタイプ

「マップ」から「支援団体連携」へ。
YOSS の支援の方向性 **B「地域資源の活用」だけが実質的に機能していない**、という一点を
示して、その直し方を提案するための動くプロトタイプです。

---

## 何のために作ったか

### 見つけた事実

実物の YOSS では、校内チーム会議で子どもごとに支援の方向性を A / B / C で記録します。

| 方向性 | 繋ぎ先 | カテゴリ名だけで足りるか |
| --- | --- | --- |
| A 教職員関与 | 校内（担任・養護・SC など） | 足りる。誰に頼むかは校内で決まっている |
| C 専門機関の活用 | 公的機関 | 足りる。繋ぎ先が制度で決まっている |
| **B 地域資源の活用** | **地域の支援団体** | **足りない** |

B の項目は「③ 居場所、こども食堂の活用」のように、どれも「◯◯の活用」というカテゴリ名です。
チェックは入れられます。記録にも残ります。でも**具体的にどの団体に繋ぐのかがシステムのどこにも無い**。
だから B は、記録された時点で行き止まりになります。

### 診断

原因は UI ではありません。**地域の支援団体がシステムの外側にいる**ことです。

地図に施設を並べても解決しません。地図に載っているのは「そこに建物がある」という事実だけで、
「今この子に何ができるか」ではないからです。B に必要なのは所在地ではなく、**対応可能な支援の中身**です。

### このプロトタイプが証明しようとしていること

支援団体を「外部の参照先」ではなく「一緒にやるプレイヤー」として YOSS の内側に入れれば、
**学校の入力を1つも増やさずに** B が機能する、ということ。

```
支援団体  ──登録──▶  YOSS  ──自動表示──▶  学校
   ▲                                        │
   └──────────── レビュー ◀────────────────┘
```

増える入力は支援団体側だけです。学校側は、既に入力しているスクリーニングがそのまま効きます。

## 設計思想

### 1. 先生に新しい入力をさせない

これが企画の主張そのものです。入力欄を1つでも足した瞬間、話は「現場にその余力があるのか」に
移り、提案そのものが死にます。

境界線はここです。**既に実物にある入力（37項目のスクリーニング、会議メモ）は使う。
本プロトタイプで新しい入力欄は足さない。**

支援候補を出すまでの流れに、先生の新しい手数はありません。

```
先生が入力する37項目  ──導出──▶  8領域スコア  ──抽出──▶  支援候補
（実物に既にある）              （手で置かない）      （8領域スコアだけを見る）
```

会議で登録するアクションも、文面・担当・方向性をすべて登録元の支援から導出していて、
`MeetingAction` に手入力のフィールドは1つもありません。

### 2. 実物の YOSS を土台にする。理想形を作らない

37項目のスクリーニング、A/B/C の方向性、「支援の現状」の項目の並び、新／続／拒 の状態。
実物にあるものは実物どおりの形で置いています。

きれいな理想形を設計してしまうと「それはうちのシステムではない」で話が終わります。
**実物のままの B 項目の並びを見せるからこそ、「ここにカテゴリ名しか無い」という指摘が刺さります。**

足したのは会議画面のタブ⑤「今回の対応記録」1つだけです（記録する場と閲覧する場を分けるため）。
タブ①〜④は実物の構成そのものです。

### 3. 真実源をひとつだけ持つ

児童データの真実源は `Student.answers`（37項目への回答）だけです。
8領域スコアも問題タグも、そこから導出します。スコアを手で置きません。

2か所に真実を持つと必ず食い違います。実際、利用実績をレビューとは別系統で持っていたときは
「利用実績なし」なのに星が付く状態が起きました（issue #22）。今は**レビューが利用実績を兼ねます**
——レビューを書けるのはその支援を使った学校だけなので、件数がそのまま実績になります。

### 4. 8領域を共通言語にする

学校適応 / 学習 / 家庭状況 / 発達 / 健康 / 経済 / 福祉 / 地域情報。
児童の状態・支援の対応範囲・レビューを、この8領域だけで繋ぎます。

支援候補の抽出も**8領域スコアだけ**で行い、問題タグを直接は見ません。
繋ぎ方が1本だと、団体が登録するときも「うちはどの領域か」だけ考えれば済みます。

### 5. 無いものは「無い」と出す

登録された支援が0件の B 項目には「登録された支援がありません」と表示します。

件数を水増しすればデモは見栄えがします。でもこの提案が示したいのは、**まさに今そこが空である**
という事実そのものです。埋めてしまったら証明したいものが消えます。

### 6. 同じ情報を二度置かない／1画面に押し込まない

会議画面は情報量が多く、放っておくと同じ情報が別の場所に何度も出ます。追加する前に、
既に出ている情報を疑います。

一方で、決まった高さに全部を収めようとするのもやめました。以前は「候補一覧だけスクロール、
領域選択は常に表示」でしたが、押し込むほど窮屈で読めませんでした。今は外枠だけビューポート高に
収め、タブの中身は素直に縦スクロールします。

## 何ができているか

| 画面 | ルート | 誰向け | 何をする |
| --- | --- | --- | --- |
| トップ | `/` | — | 提案の要約 |
| 画面A | `/register` | 支援団体 | 対応可能な支援を登録する |
| 画面C | `/dashboard` | 共通 | 支援団体ディレクトリとレビュー |
| 画面D | `/meeting` | 学校 | **校内チーム会議。ここが中心** |
| 画面E/F | `/orgs/:id`・`/orgs` | 一般 | 登録内容から自動生成される公開ページ |

画面Dは実物どおりのタブ①〜④に、⑤「今回の対応記録」を足した構成です。核心は2つです。

- **タブ②の「支援の現状」** — B の各項目に、対応する支援の**登録件数が数字で出ます**。
  ここが「カテゴリ名しか無い」状態からの変化そのものです
- **タブ④「領域と支援候補」** — 8領域ごとの支援候補。②のB項目から、その項目に対応する支援だけを
  開いた状態で飛べます

候補の並び順は、①合致した領域のスコア合計が高い順 → ②その支援へのレビュー評価が高い順。
複数領域に効く支援（子ども食堂など）が上位に来ます。「この子の困りごとを一度にカバーできる」
ものを優先する、という順序付けです。

## 触ってみる

```bash
npm install
```

```bash
npm run dev
```

ポートは決め打ちにしないでください。5173 が埋まっていると Vite が別のポートに回ります。

**見る順番**：`/`（提案）→ `/register`（支援を1つ増やす）→ `/meeting`（B項目の件数が増える）
→ `/dashboard` → `/orgs`

> デモの前に画面Aの「初期状態に戻す」を押してください。localStorage に前回の編集が残っていると
> シードの更新が反映されません（利用者の編集を勝手に上書きしないための挙動です）。

## 技術構成と制約

React 19 / TypeScript / Vite / Tailwind CSS v4 / react-router-dom。
**バックエンドはありません。** モックデータと localStorage だけで動きます。

意図的に実装していないもの：認証と権限（見ている学校は `schools.ts` の固定値）、API、
決済（画面Eの寄付は表示と集計のみ）、複数年度・複数学期、児童の実データ（すべて架空）。

コードを触る前に **[CLAUDE.md](CLAUDE.md)** を読んでください。
型を変えたら `organizationStore.migrate()` も直す、といった落とし穴が書いてあります。
経緯と決定理由は issue と PR に残しています。
