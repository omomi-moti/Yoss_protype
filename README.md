# YOSS 地域資源機能の再設計プロトタイプ

YOSS の支援の方向性 B「地域資源の活用」が機能していない理由と、その直し方を示す
動くプロトタイプです。

## 何のために作ったか

校内チーム会議では、子どもごとに支援の方向性を A / B / C で記録します。

| 方向性 | 繋ぎ先 | カテゴリ名だけで足りるか |
| --- | --- | --- |
| A 教職員関与 | 校内（担任・養護・SC など） | 足りる。誰に頼むかは校内で決まっている |
| C 専門機関の活用 | 公的機関 | 足りる。繋ぎ先が制度で決まっている |
| B 地域資源の活用 | 地域の支援団体 | 足りない |

B の項目は「③ 居場所、こども食堂の活用」のようなカテゴリ名だけで、実際にどの団体へ繋ぐのかが
システムにありません。チェックは入るが、次の行動には繋がらない。

原因は UI ではなく、支援団体がシステムの外側にいることです。地図に施設を並べても、そこに載るのは
所在地であって、今この子に何ができるかではありません。

そこで支援団体を YOSS の内側に入れます。団体が対応可能な支援を登録し、それが会議画面に候補として
自動で並び、使った学校がレビューを書く。増える入力は団体側だけです。

## 設計思想

### 1. 先生に新しい入力をさせない

入力欄を足すと、話が「現場にその余力があるのか」に移ります。境界線は、実物に既にある入力
（37項目のスクリーニング、会議メモ）は使い、新しい入力欄は足さない、というところに引きました。

```
先生が入力する37項目 ──導出──▶ 8領域スコア ──抽出──▶ 支援候補
（実物に既にある）             （手で置かない）    （これだけを見る）
```

会議で登録するアクションも、文面・担当・方向性を登録元の支援から導出します。
`MeetingAction` に手入力のフィールドはありません。

### 2. 実物を土台にする

37項目、A/B/C、「支援の現状」の項目の並び、新／続／拒。実物にあるものは実物どおりに置いています。
理想形を設計すると「それはうちのシステムではない」で話が終わるためです。

足したのは会議画面のタブ⑤「今回の対応記録」だけで（記録する場と閲覧する場を分けるため）、
①〜④は実物の構成です。

### 3. 真実源をひとつだけ持つ

児童データの真実源は `Student.answers`（37項目への回答）です。8領域スコアも問題タグもそこから
導出し、手では置きません。

以前は利用実績をレビューとは別に持っていて、「利用実績なし」なのに星が付きました（issue #22）。
今はレビューが実績を兼ねます。書けるのは使った学校だけなので、件数がそのまま実績です。

### 4. 8領域を共通言語にする

学校適応 / 学習 / 家庭状況 / 発達 / 健康 / 経済 / 福祉 / 地域情報。
児童の状態・支援の対応範囲・レビューを、この8領域だけで繋ぎます。抽出も8領域スコアだけで行い、
問題タグは見ません。

繋ぎ方が1本なので、団体が登録するときも「うちはどの領域か」だけ考えれば済みます。

### 5. 無いものは「無い」と出す

登録が0件の B 項目には「登録された支援がありません」と表示します。水増しすればデモの見栄えは
よくなりますが、示したいのは今そこが空だという事実のほうです。

### 6. 同じ情報を二度置かない

会議画面は情報量が多く、放っておくと同じ情報が別の場所に何度も出ます。追加する前に、既に出ている
情報を疑います。

一方で、決まった高さに全部を収めるのはやめました。押し込むほど窮屈で読めなかったためです。
外枠だけビューポート高に収め、タブの中身は縦スクロールします。

## 何ができているか

| 画面 | ルート | 誰向け | 何をする |
| --- | --- | --- | --- |
| トップ | `/` | — | 提案の要約 |
| 画面A | `/register` | 支援団体 | 対応可能な支援を登録する |
| 画面C | `/dashboard` | 共通 | 支援団体ディレクトリとレビュー |
| 画面D | `/meeting` | 学校 | 校内チーム会議。ここが中心 |
| 画面E/F | `/orgs/:id`・`/orgs` | 一般 | 登録内容から自動生成される公開ページ |

画面Dは実物どおりのタブ①〜④に⑤を足した構成です。中心は2つ。

- タブ②「支援の現状」— B の各項目に、対応する支援の登録件数が数字で出ます
- タブ④「領域と支援候補」— 8領域ごとの候補。②のB項目から、その項目の支援だけを開いた状態で
  飛べます

候補は、合致した領域のスコア合計が高い順、同点ならレビュー評価が高い順に並びます。
複数領域に効く支援（子ども食堂など）が上位に来ます。

## 触ってみる

```bash
npm install
```

```bash
npm run dev
```

ポートは決め打ちにしないでください。5173 が埋まっていると Vite が別のポートに回ります。

見る順番は `/`（提案）→ `/register`（支援を1つ増やす）→ `/meeting`（B項目の件数が増える）
→ `/dashboard` → `/orgs`。

デモの前に画面Aの「初期状態に戻す」を押してください。localStorage に前回の編集が残っていると
シードの更新が反映されません（利用者の編集を勝手に上書きしないための挙動です）。

## 技術構成と制約

React 19 / TypeScript / Vite / Tailwind CSS v4 / react-router-dom。
バックエンドはなく、モックデータと localStorage だけで動きます。

実装していないもの：認証と権限（見ている学校は `schools.ts` の固定値）、API、決済（画面Eの寄付は
表示と集計のみ）、複数年度・複数学期、児童の実データ（すべて架空）。

コードを触る前に [CLAUDE.md](CLAUDE.md) を読んでください。型を変えたら
`organizationStore.migrate()` も直す、といった落とし穴が書いてあります。
経緯と決定理由は issue と PR に残しています。
